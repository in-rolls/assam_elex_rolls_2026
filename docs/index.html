Where the data is

One Parquet file per constituency

The authoritative copy is gs://sawasdee-assam-rolls/shards/ — AC001.parquet … AC126.parquet, 611 MB, each beside an entry.json (counts, reconciliation, cost) and a verify.json. A byte-verified local copy sits in the repo at data/electors/.

import pandas as pd, glob
df = pd.concat(pd.read_parquet(f) for f in sorted(glob.glob("data/electors/AC*.parquet")))

One row is one printed elector box: name, relation_name, relation_type, age, sex, house_no, epic_no, roll_section (main / addition / deletion), deleted (the roll's own struck-off marking), and provenance to the page: ac_no, part_no, page_no, box_row, box_col, source_pdf, pdf_sha256.

The extraction exceeds the published net figure because it keeps what that figure removes: supplement entries and electors the roll itself marks deleted. Filtering roll_section == "main" and deleted == False approximates the net roll.

Every part of the roll prints its own closing total — a number this pipeline did not produce. Of 20,092 extracted parts, 19,259 could be measured against it and 18,688 (97.0%) match exactly; 46 constituencies match on every measured part. All recorded disagreement sums to 1,450 rows — 0.0056% — with the worst constituency at 0.100%, and each constituency's figure travels in its entry.json.

Accuracy

What is proven wrong, and what is unmeasured

Two claims, kept separate. The first is a lower bound: rows provably wrong from the data alone — an identifier repeated though unique by definition, a printed label leaked into a name, a name in the wrong script.

The EPIC rates are the dataset's weakest point and are concentrated by history: a charset defect fixed mid-run left ~46 early constituencies at the old ~4.8% malformed rate, while constituencies processed after the fix run near zero. Re-reading the affected constituencies costs ~$150 of compute and was deliberately deferred.

The second claim is not yet made: accuracy against ground truth. A row no detector condemns is unmeasured, not correct — only human marking catches a plausible wrong name. The instrument exists (a 150-crop review sheet) and is waiting to be marked.

Cost & failures

What it took

Compute: four 32-core machines, roughly $450–500 all-in, of which about $200 was idle time before utilisation was fixed. OCR: Google Cloud Vision, ~$130–150 true (a repacking design cut billed images ~9×; $103 of it survives on record). The failures that changed the design:

  1. Resume treated a part with cached OCR words but no image as unprepared — every reboot re-rendered the whole backlog. Cached words now suffice.
  2. An exact-match publish gate discarded whole constituencies over marginal shortfalls; measured distributions replaced it with structural-loss rules, pinned as tests.
  3. One OCR'd serial — 3801114767, from a "photo available" placeholder box — overflowed int32 and discarded 179k rows.
  4. Vision's batch API reports per-image failure inside HTTP 200; treated as a blank image, one night of it parked 22 constituencies. Empty answers are now failed reads.
  5. A 67-megapixel composite, accepted by the API, deterministically exceeded the OCR backend's deadline. The pixel budget now targets what the backend can process.
  6. The Barak-valley Bengali rolls title their supplements in the genitive — সংযোজনের তালিকা — which the whole-word section matcher rejected; three constituencies filed every supplement elector into the main roll before the inflected forms became markers. All three republished exact.

Operations

Shut down, restartable

All four VMs are TERMINATED — kept, not deleted, by decision (their disks cost ~$32/month and hold nothing unique; every input and output lives in the bucket). A worker is recreated by starting an instance with the repo's worker script as startup metadata; it claims work from the bucket, resumes from cached state, and publishes shards. Because OCR words are cached beside each part, a parser improvement re-reaches all 26M rows for CPU cost only.
